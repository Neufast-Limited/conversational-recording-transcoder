# Grafana k6: existing transcoder, no deployment

This test invokes the existing `conversational-media-transcoder` Lambda up to 100
times concurrently, using copies of the same one-hour recording under distinct interview IDs in
`voicebot-testing`. It does not change the Lambda configuration or create queues,
functions or roles. One k6 virtual user invokes one interview once.

| Video duration | Value |
|---|---|
| Source video per interview | **1 hour and 0.02 seconds (3,600.02 seconds)** |
| Number of test interviews | 20 or 100, each using the same source video |
| Total source media across the test | 20 hours and 0.4 seconds, or 100 hours and 2 seconds |

Video duration is the length of the recording. Transcoding time is measured
separately and may be much shorter. Final result Markdown reports should state
the source duration above and include each output MP4's measured duration beside
its processing time; do not label processing time as video duration.

Run commands from `conversational-recording-transcoder/`.

## Prepare and run

If `results/run20.json` is absent, stage the twenty inputs first. This writes only
new `interview_perftc_...` S3 prefixes (the Lambda role only permits `interview_*/*`) and does not start encoding:

```bash
uv run --with boto3 python performance-tests/transcoder_perf.py stage \
  --existing-function conversational-media-transcoder \
  --count 20 --state performance-tests/results/run20.json
```

Once staging finishes, start actual processing:

```bash
uv run --with boto3 python performance-tests/run-k6.py \
  --state performance-tests/results/run20.json \
  --output-dir performance-tests/results/k6-20 \
  --dashboard
```

For 100 concurrent encodes, stage with `--count 100`, use a fresh state filename
such as `results/run100.json`, and select a new output directory when running k6.
The VU count follows the number of staged interview IDs.

Open **http://127.0.0.1:5665** for the dashboard. An HTML copy is saved to
`performance-tests/results/k6-20/dashboard.html`. Close the dashboard browser tab
after completion if k6 waits to exit.

The wrapper automatically selects [`transcoder-direct.k6.js`](transcoder-direct.k6.js)
from the state's `mode: direct-existing`. It obtains AWS credentials using boto3's
default credential chain, including `AWS_PROFILE`, without printing credentials.
They must remain valid for the entire test. The identity needs existing-Lambda
invoke/read, test-prefix S3 write/read, and CloudWatch Logs read permissions. It
does not need deployment or IAM-role creation permissions.

## Scope and expected handler response

The production pipeline encodes and uploads the MP4 **before** checking for a
transcript. These test inputs intentionally have no transcript. After encoding,
the handler logs `TranscriptNotReady` and returns a failed-item response. This is
expected for this **encoding-only test** and stops synthetic interviews before
scoring. No completion marker is written.

k6 invokes Lambda synchronously with an SQS-shaped event. No SQS message is sent,
so the expected missing-transcript result does not create queue retries. The
produced MP4s remain in S3 for validation. Success requires the expected handler
response/log and a nonempty MP4. Setup checks there are no transcripts, existing
MP4s or done markers; each run needs fresh IDs.

This measures concurrent encoding on the existing Lambda. It does not test FIFO
scheduling, scoring or completion markers. The SQS trigger's maximum concurrency
does not apply to direct invocations; normal traffic shares the function/account
capacity. The prepared fixture is 3,600.02 seconds, 117 MB and 640×360 VP8/Opus,
made by looping real interview media into 720 byte-contiguous parts. A pass only
establishes capacity for this workload.

## Results and targets

| Metric | Meaning | Default target |
|---|---|---|
| `transcoder_completed` | Valid encoding-only responses and nonempty MP4s | 20 |
| `transcoder_failed` | Invocation, output or handler validation failures | 0 |
| `transcoder_success` | Successful encode fraction | 100% |
| `transcoder_within_sla` | Fraction within the time target | 100% |
| `transcoder_completion_seconds` | Synchronous invocation duration | p95 < 600 seconds |
| `transcoder_lambda_duration_seconds` | Duration from Lambda REPORT tails | Informational |
| `transcoder_lambda_memory_mb` | Max memory per invocation | Informational |

The default target is **ten minutes**. The request timeout is 1,000 seconds, long
enough to observe Lambda's 900-second timeout. Override the target if needed:

```bash
uv run --with boto3 python performance-tests/run-k6.py \
  --state performance-tests/results/run20.json \
  --sla-seconds 780 --max-wait-seconds 1000
```

After k6 finishes, verify output duration and actual overlap using Lambda logs:

```bash
uv run --with boto3 python performance-tests/transcoder_perf.py report \
  --state performance-tests/results/k6-20/state.json --verify \
  --output performance-tests/results/k6-20/evidence.json
```

The evidence report attributes invocations to test IDs before counting overlap,
excluding unrelated normal traffic. `PASS` requires every staged MP4 to have
audio/video and approximately 3,600-second duration, the requested number of overlapping test
invocations, and one completed attempt per interview. Logs can arrive late; repeat
the report if needed. Review `summary.json` for the separate k6 timing/SLA result.
ffprobe checks streams/duration, not perceptual lip sync or full output decoding.

## Offline checks

```bash
python3 performance-tests/run-k6.py \
  --state performance-tests/test-data/direct-dry-run-state.json --dry-run
k6 run performance-tests/signature-test.k6.js
```

These make no AWS requests. Signature vectors use fake credentials and independent
botocore calculations. Production pipeline tests also verify that an absent
transcript blocks scoring after encoding.

## Existing Grafana/Prometheus

Set `K6_PROMETHEUS_RW_SERVER_URL` and, when required,
`K6_PROMETHEUS_RW_USERNAME` / `K6_PROMETHEUS_RW_PASSWORD` in your shell, then use:

```bash
uv run --with boto3 python performance-tests/run-k6.py \
  --state performance-tests/results/run20.json \
  --output-dir performance-tests/results/k6-prometheus \
  -- --out experimental-prometheus-rw
```

Metrics carry `testid=<run_id>` and `workload=one-hour-transcoder-direct` tags.
Plot completion/failure counts, duration p95/max, success rate and memory. A
CloudWatch data source can show the function's `ConcurrentExecutions`; the
evidence report separately attributes overlap to this run's test IDs.

## Reruns and cleanup

Stage fresh IDs into a new state filename and use an empty output directory for
each run. Remove only the exact `interview_perftc_<run_id>_` S3 prefix recorded in its state
when results are no longer needed. Keep the original interview unchanged.

The earlier attempted isolated stack reached `ROLLBACK_COMPLETE`; CloudFormation
deleted all of its resources. No test-stack deployment is needed for this mode.
